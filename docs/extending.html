Building on it

An extension that adds to the catalog declares the dependency in its kempo-config.json, and subscribes to what it needs:

{
  "dependencies": ["kempo-products"],
  "hooks": { "kempo-products:ledger:added": "./hooks/ledger-added.js" }
}

Server SDK

import { getProducts, createProduct, setQuantity, addLedgerEntry } from 'kempo-products/sdk';

Every function resolves to [error, result], where error is { code, msg } or null.

FunctionPurpose
getProducts({ q, status, availability, tag, filters, ids, slugs, owner, inStock, sort, limit, offset })List and search. Returns { items, total }
getProduct(idOrSlug)One product, with its options
createProduct(data, { owner }), updateProduct(id, data, { owner }), deleteProduct(id, { owner })Manage products. owner makes them your extension's
getPrice(productId, selections)The server's price for { optionKey: choiceKey }: { unit, base, lines, currency }
addLedgerEntry({ ref, lines, note, reason, undoes, actor }), getLedger({ productId }), getLedgerEntry(ref)Change quantity and record it; see The ledger
setQuantity(id, quantity, { actor }), adjustQuantity(id, delta, { actor })Change quantity; -1 is unlimited. Atomic, and never below zero
setManagedBy(id, extension)Declare that your extension keeps this product's quantity and choice availability in step with something else
setChoiceAvailability(id, optionKey, choiceKey, available, { actor })Mark one choice in or out of stock
getTemplates, createTemplate, updateTemplate, deleteTemplate, registerTemplate(owner, definition), unregisterTemplates(owner), effectiveAttributes(product)Product templates: attributes, options and default values products made from them inherit and can add to
getProductTypes, registerProductType(owner, { key, name, description, needsShipping }), unregisterProductTypes(owner)Product types: what kind of product it is, and how it is delivered. kempo-products has "Generic Product"; kempo-shipping adds "Physical Item", kempo-credits "Credits Only"
getAttributes, registerAttribute(owner, definition), registerAttributes, unregisterAttributes(owner)Attributes
unregisterProducts(owner, { release })For uninstall: delete what you own, or hand it back to people
buildExport({ format }), importFile(text, { onMatch, dryRun })See Import and export

Shipping attributes

An extension can arrive with its own attributes, so a "vehicles" extension comes with its make and year already set up. registerAttributes is safe to call again on every update:

// install.js
import { registerAttributes } from 'kempo-products/sdk';

export default async () => {
  await registerAttributes('my-vehicles', [
    { key: 'make', label: 'Make', type: 'text' },
    { key: 'year', label: 'Year', type: 'number' },
  ]);
};
// uninstall.js
import { unregisterAttributes, unregisterProducts } from 'kempo-products/sdk';

export default async () => {
  await unregisterProducts('my-vehicles', { release: true });   // or omit release to delete them
  await unregisterAttributes('my-vehicles');
};

Ownership

Attributes and products can each belong to an extension. The owner alone can delete them or change what defines them, and people can still edit everything else, so an extension's products stay useful in the admin.

Only the owner canAnyone with the permission can still
Productchange its slug and name; delete itedit its description, price, options, tags, images, attribute values and quantity
Attributedelete it; change its key, kind, requirement or choicesrename it; change its help text and whether it is listed or filterable

Ownership only comes from the server SDK: pass your extension's name as owner. The HTTP routes never read an owner from a request, so it cannot be claimed from a browser.

Hooks

Declare them in your kempo-config.json hooks. Every payload carries actor: the extension that made the change, or '' for a person using the admin.

Guards

Guards run before the work. Edit the payload object in place to change what is saved, or throw { code, msg } to refuse; the caller receives exactly that error. Everything is validated after the guards run, so a guard cannot sneak in a value that would not otherwise be accepted.

EventPayload
kempo-products:product:before_create{ draft, userId } (editable)
kempo-products:product:before_update{ product, changes, userId } (editable)
kempo-products:product:before_delete{ product, userId }
kempo-products:ledger:before_add{ ref, lines, products, reason, note, undoes, actor }, refuse only. Answered by the extension that manages some of the products
kempo-products:attribute:before_create, before_update, before_deleterefuse only

Notifications

Notifications run after the change is committed. Nothing they do can undo it.

EventPayload
kempo-products:product:created, updated, deleted{ product, previous?, userId }
kempo-products:product:quantity_changed{ product, previousQuantity, quantity, reason }
kempo-products:ledger:added{ ref, lines, handedOver, reason, note, undoes }
kempo-products:ledger:add_failed{ ref }: an entry a manager agreed to did not happen, so it undoes what it did
kempo-products:category:created, updated, deleted{ category, previous?, products? } (products is the ids it was taken off, on delete)
kempo-products:attribute:created, updated, deleted{ attribute, previous? }

Handlers run one at a time in the order they were registered, and are awaited, so a slow one holds up the request that triggered it. A notification handler that throws is logged and does not stop the others.

Adding controls to products

An extension that sells, reserves or compares products puts a control on every product card and every product page by composition: plain files, no registration, no editing either page. The pages carry locations, and the extension fills them from a global content file in its public/ folder. The control is the extension's own custom element:

<!-- public/product-actions.global.html -->
<content location="products-scripts"><script type="module" src="/shop/components/AddToCart.js"></script></content>
<content location="products-card-actions"><k-shop-add-to-cart slot="actions"></k-shop-add-to-cart></content>
<content location="products-detail-actions"><k-shop-add-to-cart slot="actions"></k-shop-add-to-cart></content>
<content location="products-card-price"><k-sales-price slot="price"></k-sales-price></content>
<content location="products-detail-price"><k-sales-price slot="price"></k-sales-price></content>
LocationWhat goes there
products-scriptsThe <script type="module"> that defines your element. It loads on product pages only, outside the card template, so it runs once
products-card-actionsYour element, in the one card template, for the card's actions slot (under the price). Each card gets its own copy
products-card-priceAn element for the card's price slot: it replaces the price shown
products-detail-actionsYour element for a product page's actions slot (under the options)
products-detail-priceAn element for a product page's price slot: it replaces the price line
products-detail-extraYour element for a product page's extra slot (under the description)

A location is a plain insertion point: the element you put in it names the slot it fills with slot="…", as any child of a web component does. The price slots have the usual price as their default content, so a site that installs nothing shows it unchanged, and an extension that shows it differently (a sale price with the old one struck through, in green) puts its own element there and the default is replaced. Read card.product and card.config (on a product page page.product, page.price, page.config and page.money(minor)) and format with displayMoney from /products/sdk.js. Two extensions that both fill price are both shown, so a price override is something one extension should own.

When the browser creates your element it finds where it sits and reads what it needs from there:

// inside a card
const card = this.closest('k-products-card');
card.getAttribute('product-id');   // which product
card.product;                      // the product the list already loaded: no need to fetch it again

// on a product page
const page = this.closest('k-products-detail');
page.product; page.selections; page.price; page.complete;      // the options chosen so far, and the price they make
page.addEventListener('selection-change', this.update);        // when they change

A component that needs more than the product (stock, ratings) fetches it from its own extension's API using product-id. Several extensions can fill the same location at once and stack by priority, highest first; that is the difference from a fragment, which has one winner.

/products/ already has the card template. A page of your own that embeds a <k-products-list> includes it once, with <fragment name="products-card-template" />; without it the cards show no extension content. A list can carry its own instead, as a child: <k-products-list><template>…</template></k-products-list>.

Deprecated: registerProductAction('k-my-element') from /products/components/actions.js still works for extensions that have not moved, but it will be removed in a later major release. Use the locations above.

Adding to the pages

A tab on the product form

The admin product form is split into tabs: Details, Description, Media and Options. Any extension can add its own, such as a shipping, SEO or tax tab. Ship a global content file in your package's admin/ directory that pushes a <k-products-tab> into the products-admin-product-tabs location. Kempo picks it up without any registration, and it disappears when your extension is disabled.

<!-- admin/product-tab.global.html -->
<content id="my-extension-product-tab" name="Shipping tab" owner="my-extension" enabled="true" locked="true" location="products-admin-product-tabs" priority="10">
<k-products-tab name="shipping" label="Shipping">
  <script type="module" src="/my-extension/components/ShippingAttributes.js"></script>
  <my-shipping-attributes></my-shipping-attributes>
</k-products-tab>
</content>

Tabs from several extensions all appear, after the built-in ones, ordered by priority. Your element finds the form with this.closest('k-products-form') and listens to what is going on:

Event on the formWhenevent.detail
draft-changeThe form is edited{ changed, draft }
product-savedThe product has been stored{ product, created, waitUntil }. A tab with more to save calls waitUntil(promise) and the page waits for it before leaving
 
const form = this.closest('k-products-form');
form.addEventListener('product-saved', event => {
  event.detail.waitUntil(saveMyOwnThing(event.detail.product.id));
});

Buttons on the product and category pages

Two more places take buttons, with slots rather than injection. The product edit and new pages have a products-admin-product-actions location inside the form: an element with slot="actions" appears beside Save and Cancel, finds the form with this.closest('k-products-form'), and reads productId (empty until the product exists, so wait for product-saved on the new page) and original.

The category list has one template holding a products-admin-category-actions location, which the list makes into a row control in every row. Your element carries slot="after", so the table puts it in each row after the edit and delete controls, and it finds its category from its row. Load your module from the products-admin-scripts location, which sits outside every template.

Under the public pages

The public pages are extended with fragments: a file named after a fragment the page includes, in your own package, which kempo also picks up without registration.

FragmentWhere it appearsPut it in
products-list-extraUnder the public product listpublic/products-list-extra.fragment.html
products-detail-extraUnder a public product pagepublic/products-detail-extra.fragment.html

A fragment has one winner, chosen by an optional priority on its wrapper, so use one that is specific to your extension.
