Building on it

An extension that adds to the catalog declares the dependency in its kempo-config.json, and subscribes to what it needs:

{
  "dependencies": ["kempo-products"],
  "hooks": { "kempo-products:purchase:recorded": "./hooks/purchase-recorded.js" }
}

Server SDK

import { getProducts, createProduct, setStock, recordPurchase } from 'kempo-products/sdk';

Every function resolves to [error, result], where error is { code, msg } or null.

FunctionPurpose
getProducts({ q, type, status, availability, tag, filters, ids, slugs, owner, inStock, sort, limit, offset })List and search. Returns { items, total }
getProduct(idOrSlug)One product, with its options
createProduct(data, { owner }), updateProduct(id, data, { owner }), deleteProduct(id, { owner })Manage products. owner makes them your extension's
getPrice(productId, selections)The server's price for { optionKey: choiceKey }: { unit, base, lines, currency }
recordPurchase(data, { manual }), reversePurchase(ref), getPurchase(ref), getPurchases()See Purchases and stock
setStock(id, stock, { actor }), adjustStock(id, delta, { actor })Change stock; -1 is unlimited. Atomic, and never below zero
setManagedBy(id, extension)Declare that your extension keeps this product's stock and choice availability in step with something else
setChoiceAvailability(id, optionKey, choiceKey, available, { actor })Mark one choice in or out of stock
getTypes, registerType(owner, { name }), unregisterTypes(owner)Product types
getFields, registerField(owner, definition), registerFields, unregisterFields(owner)Fields. definition.productType scopes one to a type
unregisterProducts(owner, { release })For uninstall: delete what you own, or hand it back to people
buildExport({ format }), importFile(text, { onMatch, dryRun })See Import and export

Shipping a type and its fields

An extension can arrive with a ready-made type, so a "vehicles" extension comes with a Vehicle type already set up. registerType and registerFields are safe to call again on every update:

// install.js
import { registerType, registerFields } from 'kempo-products/sdk';

export default async () => {
  await registerType('my-vehicles', { name: 'Vehicle' });
  await registerFields('my-vehicles', [
    { key: 'make', label: 'Make', type: 'text', productType: 'vehicle' },
    { key: 'year', label: 'Year', type: 'number', productType: 'vehicle' },
  ]);
};
// uninstall.js
import { unregisterFields, unregisterTypes, unregisterProducts } from 'kempo-products/sdk';

export default async () => {
  await unregisterProducts('my-vehicles', { release: true });   // or omit release to delete them
  await unregisterFields('my-vehicles');
  await unregisterTypes('my-vehicles');
};

Ownership

Types, fields and products can each belong to an extension. The owner alone can delete them or change what defines them, and people can still edit everything else, so an extension's products stay useful in the admin.

Only the owner canAnyone with the permission can still
Productchange its slug, name and type; delete itedit its description, price, options, tags, images, field values and stock
Typerename it; delete itchange its description and position
Fielddelete it; change its key, kind, requirement or choicesrename it; change its help text and whether it is listed or filterable

Ownership only comes from the server SDK: pass your extension's name as owner. The HTTP routes never read an owner from a request, so it cannot be claimed from a browser.

Hooks

Declare them in your kempo-config.json hooks. Every payload carries actor: the extension that made the change, or '' for a person using the admin.

Guards

Guards run before the work. Edit the payload object in place to change what is saved, or throw { code, msg } to refuse; the caller receives exactly that error. Everything is validated after the guards run, so a guard cannot sneak in a value that would not otherwise be accepted.

EventPayload
kempo-products:product:before_create{ draft, userId } (editable)
kempo-products:product:before_update{ product, changes, userId } (editable)
kempo-products:product:before_delete{ product, userId }
kempo-products:type:before_create, before_update, before_deleterefuse only
kempo-products:field:before_create, before_update, before_deleterefuse only

Notifications

Notifications run after the change is committed. Nothing they do can undo it.

EventPayload
kempo-products:product:created, updated, deleted{ product, previous?, userId }
kempo-products:product:stock_changed{ product, previousStock, stock, reason }
kempo-products:purchase:recorded{ purchase }
kempo-products:purchase:reversed{ purchase }
kempo-products:type:created, updated, deleted{ type, previous? }
kempo-products:field:created, updated, deleted{ field, previous? }

Handlers run one at a time in the order they were registered, and are awaited, so a slow one holds up the request that triggered it. A notification handler that throws is logged and does not stop the others.

Adding to the pages

A page cannot define a <location> of its own, so extensions add to products' pages through fragments: a file named after a fragment the page includes, in your own package, which kempo picks up without any registration.

FragmentWhere it appearsPut it in
products-admin-product-panelsThe admin product form, above the Save buttonadmin/products-admin-product-panels.fragment.html
products-list-extraUnder the public product listpublic/products-list-extra.fragment.html
products-detail-extraUnder a public product pagepublic/products-detail-extra.fragment.html

A fragment has one winner, chosen by an optional priority on its wrapper, so use one that is specific to your extension. The admin form also tells a panel what is going on:

Event on the formWhenevent.detail
draft-changeThe form is edited{ changed, draft }
product-savedThe product has been stored{ product, created, waitUntil }. A panel with more to save calls waitUntil(promise) and the page waits for it before leaving
 
const form = document.querySelector('k-prod-form');
form.addEventListener('product-saved', event => {
  event.detail.waitUntil(saveMyOwnThing(event.detail.product.id));
});

On the public pages, <k-prod-card> and <k-prod-detail> have slots (actions, extra) and <k-prod-detail> fires selection-change, which is how a buy button learns which options are chosen. See Components.
